# Architecture & System Contract — 360 Cloud Board

This document is the living contract for **360 Cloud Board**. It is updated at the conclusion of every build phase and serves as the single architectural truth across all sessions.

---

## 1. Overview

**360 Cloud Board** is an internal system of record for work and customer interaction used across every function in the company (Dev, QA, BA, Customer Support, Customer Success, Sales, Marketing). 

It bridges multi-team workflows by:
1. Providing a generic, customizable Work Item engine with per-team display labels and custom fields.
2. Allowing direct cross-team linking (e.g., Support Ticket linked to a Dev Task).
3. Providing additive, optional Org-level modules for the **Customer Journey** (Module A) and **Product Lifecycle** (Module B) without overriding local team processes.

### Architectural Decision: Serverless-Safe Cached MongoDB Connection
- **Challenge:** Vercel functions are stateless and ephemeral. Creating a new Mongoose connection per request causes connection pool exhaustion on MongoDB Atlas and adds severe latency to cold starts.
- **Solution:** We implement a connection caching pattern on `globalThis.mongooseConnection` in [`src/lib/mongodb.ts`](file:///c:/Users/Utkarsh/OneDrive%20-%20360%20DEGREE%20CLOUD%20TECHNOLOGIES%20PRIVATE%20LIMITED/Documents/Github/360-Cloud-Board/src/lib/mongodb.ts). Warm serverless invocations reuse the established connection instantly, while cold starts share a single pending connection promise across concurrent requests. If connection fails, the promise is reset to enable graceful retries on subsequent requests.

### Architectural Decision: Mongoose for Schema Modeling
- **Rationale:** While MongoDB is schema-flexible, internal multi-team enterprise tools require strict schema invariants (e.g. Org ID scoping, audit log immutability, enum validation for status categories). Mongoose provides middleware hooks, strong schema validation, and typed document models while preserving schema extensibility for custom team fields.

## 3. Non-Negotiables

These rules are **absolute** and checked against at the end of every phase:

1. **Server-side permission checks**: Every permission check happens server-side (API route / server action). A direct API call from an unauthorized role must fail exactly like a blocked UI action would.
2. **No secrets in source control**: All credentials via environment variables; `.env.example` lists names only, never real values.
3. **Passwords hashed (bcrypt)**: Never stored or logged in plaintext.
4. **Org+Team scoped queries**: Every query returning Team, Work Item, or Customer data is scoped by Organization and Team, even though v1 has one Organization — write every query as if there were many.
5. **Append-only change history**: No route may update or delete a history record, for any role, including Org Admin.
6. **Generic engine, no bespoke paths**: New Team types or Work Item templates are added through the existing generic engine (config), never a hard-coded path for one team.
7. **Real UI states**: Every UI view ships with real loading, empty, and error states — no screen may show nothing or spin forever.
8. **Clean build**: `npm run build` passes cleanly before a phase is considered done.
9. **`requireTeamRole()` is the canonical Team-permission enforcement point** (Phase 3, [`src/lib/authz.ts`](file:///c:/Users/Utkarsh/OneDrive%20-%20360%20DEGREE%20CLOUD%20TECHNOLOGIES%20PRIVATE%20LIMITED/Documents/Github/360-Cloud-Board/src/lib/authz.ts)): every route or Server Action that gates a Team-scoped action must call `requireTeamRole(teamId, minimumRole)` (or `requireOrgAdmin()` for Org-Admin-only, non-Team-scoped actions like Team creation). A route that reimplements a role check inline — comparing `orgRole`/membership itself instead of calling through this function — is a bug, even if it happens to produce the same result today.
10. **Every status must carry an Org-level category before a Team goes live** (ORG-7, Phase 7): the `Workflow` schema makes `statuses[].category` a required enum field (`src/models/Workflow.ts`) and `PUT /api/teams/[teamId]/workflow` (`src/lib/status-categories.ts`) rejects a save without one — there is no code path that can persist a status with no category, so this is enforced structurally, not by convention or a migration script. A new Team's workflow configuration screen (`/settings/teams/[teamId]/work-item-config`) is the *only* place statuses are defined, and it always requires a category per status; there is no separate "map it later" step. Priority has no per-Team equivalent to normalize — it's a single fixed Org-level scale (`PRIORITIES` in `src/lib/status-categories.ts`) every Team already writes to directly.
11. **Guest boundary enforced server-side on every route, including list/search endpoints** (MB-3/MB-4, Phase 8): a Member with only a Guest grant — no real `TeamMembership` role anywhere — must get a real 403 on any Team-scoped route for a Work Item not explicitly shared with them, identical to the 403 an unrelated plain Member would get, so the response can never be used to distinguish "doesn't exist" from "exists but isn't shared with you." `requireWorkItemAccess()` (`src/lib/guest-access.ts`) is the single place a Guest grant is allowed to widen access beyond `requireTeamRole`, and it only ever widens access to one specific Work Item (or the Work Items under one specific Initiative) — never a Team's list, board, or dashboard. Every Team-wide list/board/dashboard route is untouched Phase 3-era `requireTeamRole`, which already returns 403 to a Member with no Team role, Guest or not.
12. **A written test schedule before a phase is considered done** (added by direct user request, August 17, 2026): Non-Negotiable #8's clean build proves the code *compiles*, not that its *behavior* is correct. Every non-trivial phase/feature must produce a concrete, written checklist of what to verify — which flows, which roles, which empty/error states, manual click-through steps and/or automated checks — logged in that phase's Build Log entry (see the "Verification" paragraph convention already established in every entry from Phase 10 on). A phase isn't done when the build is clean; it's done when the build is clean *and* the test schedule for it has been executed (or, if a live environment genuinely isn't available, explicitly logged as a stated open gap — never silently skipped or implied-but-unstated).

### `StageTrack` (added Phase 16 — Design 1, generalizes the two `Organization.module*Enabled` booleans + fixed `module-stages.ts` arrays)
MG-1/MG-2/MG-3 generalized: one document per `(organizationId, entityType)` — a named, fully editable, Org-Admin-managed stage list that can target **any** entity type, not just Customer/Initiative. Unique index on `{organizationId, entityType}` — exactly one Stage Track per entity type, extensible to a 5th/6th entity type later with zero schema change (MG-3, now realized literally).
| Field | Type | Notes |
| :--- | :--- | :--- |
| `organizationId` | `ObjectId` → `Organization` | Non-Negotiable #4. |
| `entityType` | `"customer" \| "initiative" \| "team" \| "work_item"` | Unique with `organizationId`. Which entity's macro-stage field (`Customer.journeyStage`, `Initiative.lifecycleStage`, `Team.macroStage`, `WorkItem.macroStage`) this track governs. |
| `name` | `string` | Editable display name, e.g. "Customer Journey" — was a hardcoded label in the old `ModuleToggles` UI copy; now data. |
| `enabled` | `boolean`, default `false` | Same "invisible, not disabled" semantics `moduleJourneyEnabled`/`moduleLifecycleEnabled`/`Team.sprintsEnabled` already established — disabling never deletes the underlying macro-stage values, the UI just stops showing/offering them. |
| `stages` | `[{ key: string, label: string }]` | Fully CRUD-editable — add/rename/reorder/remove — unlike the old fixed `JOURNEY_STAGES`/`LIFECYCLE_STAGES` constant arrays. | `createdBy` | `ObjectId` → `Member` | |
| `createdAt` / `updatedAt` | `Date` | Mongoose `{ timestamps: true }`. |

**Seeded on bootstrap/first migration**: 4 rows — `customer` (stages copied from the former `JOURNEY_STAGES`, `enabled` copied from `Organization.moduleJourneyEnabled`), `initiative` (from `LIFECYCLE_STAGES`/`moduleLifecycleEnabled`), `team` and `work_item` (new, empty `stages: []`, `enabled: false`) — so an existing installation sees zero behavior change until an Org Admin opts into the two new tracks or edits an existing one's stage list. `src/lib/stage-tracks.ts` replaces the deleted `src/lib/module-stages.ts`, reading the live `StageTrack` docs (cached per-request, same pattern `getEffectiveWorkflow()` uses) instead of fixed constant arrays.

**API** (`src/app/api/stage-tracks/`): `GET /` (any Member — needed to render pickers); `PATCH /[trackId]` (`requireOrgAdmin`, Zod-validated-list pattern mirroring `PUT /api/teams/[teamId]/workflow` — unique stage keys, non-empty labels, a 409 + live-usage count if a stage key currently in use by a document is removed/renamed, mirroring `Workflow`'s transition referential check). No `POST`/`DELETE` — the 4 rows are fixed by `entityType`; only their `name`/`enabled`/`stages` contents are editable.

**Stage-change routes**, extending the existing `journey-stage`/`lifecycle-stage` PATCH pattern with two new siblings, both `requireOrgAdmin`-gated (same floor as the two existing routes) and logged through the same `ChangeHistory` mechanism (CJ-2/PL-2 pattern, extended to two more entity types): `PATCH /api/teams/[teamId]/macro-stage` (Team) and `PATCH /api/teams/[teamId]/work-items/[itemId]/macro-stage` (Work Item).

### `Counter` (added post-v1)
Generic atomic-sequence store — one document per named counter. Currently only used for `WorkItem.key` (`key: "workitem:<teamId>"`), via `findOneAndUpdate` + `$inc` + `upsert` (a single atomic Mongo op, so concurrent creates on the same Team never collide). Never decremented, so a value handed out is never reissued even if whatever it numbered gets deleted.

### `WorkLog` (added August 18, 2026 — WL-1–WL-5, direct user override of REQUIREMENTS.md's former "Time tracking / worklogs" non-goal)
One row per logged entry against a Work Item — deliberately **not** one row per (item, member, day): multiple entries per person/item/day are allowed (confirmed with the user), and deliberately **not** a `ChangeHistory` `field_change` row either — `ChangeHistory` is a hard, append-only invariant (Non-Negotiable #5), but a logged entry must itself be correctable by whoever logged it (or a Team Admin), which only an ordinary mutable model can support. This is the one collection in the app outside `ChangeHistory` that a Member can edit/delete their own past write to.
| Field | Type | Notes |
| :--- | :--- | :--- |
| `organizationId` | `ObjectId` → `Organization` | Non-Negotiable #4. |
| `teamId` | `ObjectId` → `Team` | |
| `workItemId` | `ObjectId` → `WorkItem` | |
| `memberId` | `ObjectId` → `Member` | Who logged it. |
| `date` | `Date` | Calendar day the work was done, stored at UTC midnight — day granularity, not a timestamp. Computed explicitly in UTC (`startOfUtcDay()` in the `work-logs` routes) rather than the server's local timezone, unlike the pre-existing `startOfDay`/`endOfDay` local-timezone bug Phase 14's Build Log flagged in `computeBurndown()`. |
| `amount` | `Number`, min `0` | Value in `unit` below — story points, or minutes for hours/minutes. |
| `unit` | `"story_points" \| "hours_minutes"` | Snapshotted at entry time, not read live from `Team.timeTrackingUnit` — protects historical entries if a Team's unit is ever changed (though in practice `PATCH /api/teams/[teamId]/time-settings` refuses a unit change while any `WorkLog` row exists for that Team, so every row for a Team always agrees with its current setting). |
| `note` | `String`, optional | Freeform, what was done. |
| `createdAt` / `updatedAt` | `Date` | Mongoose `{ timestamps: true }`. |

Indexes: `{ workItemId: 1, date: 1 }`, `{ teamId: 1, date: 1 }`. **Cascade-deleted with its Work Item** — found during live verification and fixed the same session: unlike `ChangeHistory`/`Attachment` (deliberately not cascade-deleted, audit-trail-like data that outlives its subject), a `WorkLog` row has no meaning or reachable UI once its Work Item is gone, so `DELETE /api/teams/[teamId]/work-items/[itemId]` now also runs `WorkLog.deleteMany({ workItemId })` alongside the existing sub-task-orphaning step.

**API** (`src/app/api/teams/[teamId]/work-items/[itemId]/work-logs/`): `GET /` (`requireTeamRole(teamId, "viewer")` — matches the Roles & Permissions Matrix's "View Team's items, boards, reports: Viewer = Yes"); `POST /` (`requireTeamRole(teamId, "member")`, 400 if the Team has no `timeTrackingUnit` configured); `PATCH`/`DELETE /[entryId]` (owner-or-Team-Admin — a correction-rights floor with no exact precedent elsewhere in this codebase, since comments/attachments aren't user-editable at all; the natural reading of "any Team Member+ can log time" plus a normal admin override). Every mutation also calls `recomputeWorkItemActualTotal()` (`src/lib/work-log-reports.ts`) synchronously in the same request, and `recordWorkLogChange()` (`src/lib/work-item-history.ts`) to leave the `ChangeHistory` breadcrumb described above. `GET /api/teams/[teamId]/work-logs/export` (`requireTeamRole(teamId, "viewer")`) is an RP-5-style CSV export of a Team's logged time over a date range, built on the existing `rowsToCsv`/`csvResponse` helpers (`src/lib/csv.ts`).

**Unit-change lock**: `PATCH /api/teams/[teamId]/time-settings` rejects a `timeTrackingUnit` change with a 409 + live count if the Team already has any `WorkLog` row — same referential-integrity convention `Workflow`'s transition-removal check and `StageTrack`'s stage-removal check already use, here preventing a Team from making its own historical Actuals unsummable.

**Real-time rollup (WL-4), not a scheduled recompute**: `WorkItem.actualTotal` (see the `WorkItem` entry above) is a denormalized sum of a Work Item's `WorkLog` rows, kept in sync by `recomputeWorkItemActualTotal()` on every add/edit/delete — chosen over a live aggregate-on-read value or a cron job per direct user request (the user's own words: "let the values be rolled-up in realtime and updated in the db alongwith the already saving function daily" / "automatic only"). `computeEstimateVsActual()` (same file) — the source for the `estimate_vs_actual` Dashboard widget (WL-5, `src/components/dashboard/estimate-vs-actual-table.tsx`, wired into the existing configurable-widget registry `src/lib/dashboard-widgets.ts`/`dashboard-view-schema.ts`/`widget-grid.tsx` — same "one registry entry + one case" pattern Non-Negotiable #6 established) — reads `estimate`/`actualTotal` directly off `WorkItem`, no `WorkLog` aggregation at read time.

| `workItemId` | `ObjectId` → `WorkItem`, nullable | Set only for `scope: "work_item"`. |
| `teamId` | `ObjectId` → `Team`, nullable | Denormalized from `workItemId` at grant time — lets the grant-permission check (Team Admin "own Team's items," Team Member "items they own") skip a join. |
| `initiativeId` | `ObjectId` → `Initiative`, nullable | Set only for `scope: "initiative"`. A grant here reaches *every* Work Item currently tagged to that Initiative, resolved live (`hasGuestAccessToWorkItem()` in `src/lib/guest-access.ts`), not a snapshot at grant time. |
| `grantedBy` | `ObjectId` → `Member` | |
| `createdAt` / `updatedAt` | `Date` | Mongoose `{ timestamps: true }`. |

One grant per `(memberId, workItemId)` and per `(memberId, initiativeId)` (unique partial indexes) — re-granting the same target is idempotent, not a duplicate row. Granting is gated by `requireTeamRole(teamId, "member")` plus an ownership check (`item.reporter === requester`) for a plain Team Member, or `requireTeamRole(teamId, "admin")`-equivalent for a Team Admin (`POST /api/teams/[teamId]/work-items/[itemId]/guests`); Initiative-level granting reuses `requireAnyTeamAdmin()`, the same rule Initiative creation itself uses (Phase 7 precedent) — `POST /api/initiatives/[initiativeId]/guests`.

### `Sprint` (implemented Phase 9; **deleted Phase 16** — folded into `Initiative`, see above)
**Retired.** BD-3/BD-4's Team-scoped Scrum planning container used to be its own model; as of Phase 16 (Design 2, by direct user request) it no longer exists as a separate collection or Mongoose model — its fields (`teamId`, `goal`→`sprintGoal`, `startDate`, `endDate`, `status`→`sprintStatus`) live on `Initiative` instead, active only when `Initiative.teamId` is set (a "Team-run Initiative"). `src/lib/sprints.ts`'s `getActiveSprint()`/`startSprint()`/`completeSprint()` and `src/lib/sprint-reports.ts`'s `computeBurndown()`/`computeVelocity()` keep their exact names, signatures, and invariants (one `active` per Team; rollover to the next `planned` Team-run Initiative or the backlog; a completed one's remaining items are exactly the finished ones) but now query `Initiative` filtered by `{teamId, sprintStatus}` instead of a separate `Sprint` collection. The old `sprints` Mongo collection itself is **not** dropped (see the migration note under `Initiative` above); this section is kept, unedited in substance below, purely as the historical record of what `Sprint`'s schema looked like before the fields moved.
| Field | Type | Notes |
| :--- | :--- | :--- |
| `organizationId` | `ObjectId` → `Organization` | Non-Negotiable #4. |
| `teamId` | `ObjectId` → `Team` | |
| `name` | `string` | |
| `goal` | `string` | Optional, freeform. |
| `startDate` / `endDate` | `Date` | Set at creation; editable via `PATCH .../sprints/[sprintId]` only while `status: "planned"` — once a Sprint starts, its planned window is history, not a draft. |
| `status` | `"planned" \| "active" \| "completed"` | The lifecycle source of truth (BD-4). At most one `"active"` Sprint per Team, enforced in `src/lib/sprints.ts` (`startSprint()`) as a cross-document invariant, not a schema constraint. |
| `createdBy` | `ObjectId` → `Member` | |
| `createdAt` / `updatedAt` | `Date` | Mongoose `{ timestamps: true }`. |

**Completing a Sprint** (now: completing a Team-run Initiative — `completeSprint()` in `src/lib/sprints.ts`, `POST /api/initiatives/[initiativeId]/complete`) moves every item whose status category isn't `done` to the next `"planned"` Team-run Initiative for that Team (earliest `startDate`) or, if none exists, back to the backlog (`teamInitiativeId: null`) — BD-4's rollover, and the reason a closed one's remaining `WorkItem`s are exactly the ones that were actually finished (see Velocity below). The rollover is recorded into `ChangeHistory` (`field: "teamInitiativeId"`, renamed from `"sprintId"`) exactly like a manual reassignment would be (CT-1), attributed to whoever clicked "Complete."

**Reporting** (`src/lib/sprint-reports.ts`, RP-1/RP-2), both built on data already in the system rather than a new snapshot mechanism:
- **Burndown** (`computeBurndown()`): remaining item COUNT per day (not story points — WF-2 custom fields are optional per Team, so a points field isn't guaranteed to exist anywhere; count is the one unit every Team has, ORG-4), reconstructed by replaying each item's `field: "status"` `ChangeHistory` entries against the Team-run Initiative's current item membership. Documented scope limit, unchanged since Phase 9: an item manually pulled out mid-flight (not via the Complete rollover, which keeps it assigned) drops out of the whole reconstruction rather than just the day it left.
- **Velocity** (`computeVelocity()`): last N completed Team-run Initiatives, each one's count is a plain `WorkItem.countDocuments({ teamInitiativeId })` (filtered defensively by `category === "done"`) — no snapshot needed, because rollover already guarantees only the finished items remain assigned to a closed one.

### `Attachment` (implemented, Phase 10)
IT-9/IT-10/IT-11: file attachments on a Work Item, stored in Vercel Blob. Own collection, not embedded on `WorkItem` — same "reference lives on the child" pattern as `WorkItemLink`/`Customer`/`Initiative`.
| Field | Type | Notes |
| :--- | :--- | :--- |
| `organizationId` | `ObjectId` → `Organization` | Non-Negotiable #4. |
| `teamId` | `ObjectId` → `Team` | Denormalized from the Work Item at upload time, same rationale as `GuestGrant.teamId` — lets the list/delete routes stay a single-collection query. |
| `workItemId` | `ObjectId` → `WorkItem` | |
| `filename`, `contentType`, `size` | `string`, `string`, `number` | Captured from the uploaded `File` at write time. |
| `blobUrl`, `blobPathname` | `string`, `string` | Vercel Blob's public URL (rendered directly — no download-proxy route needed) and pathname (needed for `del()` on delete). |
| `uploadedBy` | `ObjectId` → `Member` | |
| `groupId` | `ObjectId` | Basic versioning (phase brief): every version of "the same" attachment shares a `groupId`, set to the `_id` of its first version. Re-uploading (`replacesAttachmentId` in the POST body) inserts a **new** document rather than overwriting one — a previous version is a real row, not destroyed, only flagged `isLatest: false`. |
| `version` | `number` | Increments per re-upload within a `groupId`. |
| `isLatest` | `boolean` | The panel's default list (`GET .../attachments`) filters to this — a `?groupId=` query on the same route returns every version for the "N earlier versions" expandable list. |
| `deletedAt` | `Date`, nullable | Soft-delete. `DELETE .../attachments/[attachmentId]` removes the **whole group** (every version), not one version — the spec describes deleting "an attachment," not resurrecting an older version after its group is gone — flagging every version's `deletedAt` and calling Blob's `del()` on each one's `blobPathname`. |
| `createdAt` / `updatedAt` | `Date` | Mongoose `{ timestamps: true }`. |

**Permissions match the Work Item itself, with zero new authz code**: `GET` (list) goes through `requireWorkItemAccess()` — the existing single Guest-widening enforcement point (MB-4) already used by the item/history/comments routes — so a Team Viewer or a Guest with a grant on this item can both see and download. `POST` (upload) and `DELETE` call `requireTeamRole(teamId, "member")` directly, exactly like the Work Item's own `PATCH`/`DELETE` — this alone excludes Guest (not a `TeamRole`) and plain Viewer (rank too low), which **is** "Viewer/Guest can download but not delete" — no separate capability-check helper was needed, the two existing enforcement points already say it between them.

**Paste/drag-drop into the description or a comment** (`src/lib/attachment-upload.ts`, shared by the panel's upload button and both textareas): uploads the file through the same `POST` route, then inserts a `![filename](blobUrl)` Markdown reference at the cursor. The description already renders through `react-markdown`+`remark-gfm`, so this needed no new renderer. Comments render through a plain `@mention`-highlighting text splitter, not Markdown, and the two don't compose — rather than switching comments to a full Markdown renderer (which would need to re-implement mention highlighting on top of it), `history-feed.tsx` pulls `![alt](url)` image references out of `commentText` with a small regex first, renders those as real inline thumbnails, and still runs the *remaining* text through the unchanged mention splitter.

### `SavedView` (added post-v1)
A named, persisted filter/sort/group-by config for one Team's Work Items of one type — see `ViewConfig` in `src/lib/work-item-views.ts` (also exports `buildFilterQuery()`, `applySort()`, `applyGroupBy()`, and the URL encode/decode helpers). The current (possibly-unsaved) config always lives in the URL as `?view=<JSON>`, read/written by `ViewToolbar` (`src/components/work-items/view-toolbar.tsx`) — so it's shareable/bookmarkable and the page loader builds the query/sort/grouping from a plain `searchParams` read, no client round-trip on first render.
| Field | Type | Notes |
| :--- | :--- | :--- |
| `organizationId` | `ObjectId` → `Organization` | |
| `teamId` | `ObjectId` → `Team` | |
| `type` | `string` | The Work Item type this View applies to (`"task"`/`"ticket"`). |
| `name` | `string` | |
| `createdBy` | `ObjectId` → `Member` | |
| `visibility` | `"self" \| "team"` | `"self"` — only the creator ever sees it in their Views menu. `"team"` ("for all") — every Member with access to the Team sees it too. Creating a `"team"` View requires Team Member+ (a Viewer may only save `"self"` Views, so they can't clutter everyone else's menu); editing/deleting a `"team"` View someone else made requires its creator or a Team Admin. |
| `config` | `Mixed` (`ViewConfig`) | `{ filters, sort, groupBy }` — stored wholesale like `WorkItem.customFields`, never queried field-by-field. |
| `createdAt` / `updatedAt` | `Date` | |

**Filter shape is deliberately two-level, not an arbitrary recursive tree**: groups combined with AND, conditions within a group combined with OR (`(status is To Do OR In Progress) AND assignee is me`) — covers the overwhelming majority of real filters without the UI complexity a fully recursive builder needs. Every multi-select-style field (`status`/`priority`/`assignee`/`reporter`/`labels`/`customerId`/`initiativeId`/`sprintId`) uses `is_any_of`/`is_none_of`; `dueDate` is the one field with its own operator set (`before`/`after`/`is_empty`/`is_not_empty`). `buildFilterQuery()` turns this straight into a Mongo query merged alongside `teamId`/`type`. **Sort and group-by are applied in JS after the fetch, not via Mongo**, since `status`/`priority` need semantic order (a Team's own workflow category rank, the fixed Org-level priority scale) that only a JS comparator with the right context (the Team's resolved `Workflow`, a `memberNames` map) can express — see `applySort()`/`applyGroupBy()`.

**Board view gets filtering only** (`ViewToolbar`'s `showSortAndGroup={false}`) — its columns are always Status, sort is drag-managed via `WorkItem.order`, and "group by" would mean a different column dimension entirely, judged a bigger visual rework than this pass covers, not a gap.

### `DashboardView` (added post-v1, deliberate DB-3 override; widget instances + Team Dashboards added same day)
A named, persisted selection + order of widget **instances** — see `DashboardViewConfig`/`WidgetInstance` in `src/lib/dashboard-views.ts`/`src/lib/dashboard-widgets.ts`. Serves **both** `/dashboard` (Org-level, `teamId: null`) and a Team's own `/teams/[teamId]/dashboard` (`teamId` set) — one model for both surfaces rather than forking a second one, since the only real difference between them is which scope a View belongs to. Same URL-carried-working-config pattern `SavedView` established (`?dv=<JSON>`, read/written by `DashboardViewToolbar` — `src/components/dashboard/dashboard-view-toolbar.tsx`).
| Field | Type | Notes |
| :--- | :--- | :--- |
| `organizationId` | `ObjectId` → `Organization` | |
| `teamId` | `ObjectId` → `Team`, nullable | `null` = an Org-level View (`/dashboard`); set = that Team's own View (`/teams/[teamId]/dashboard`). Unlike `SavedView.teamId` (always required — a Work Item list View always belongs to one Team), this is optional because a Dashboard View can belong to either surface. |
| `name` | `string` | |
| `createdBy` | `ObjectId` → `Member` | |
| `visibility` | `"self" \| "shared"` | Not `"self" \| "team"`/`"org"` as two separate enums — one value, whose meaning depends on `teamId`: `"shared"` on an Org-level View (`teamId: null`) reaches every Member in the Organization; on a Team-level View it reaches every Member with access to that Team. **`teamId: null` sharing has no Org-Admin/Team-Admin gate at create time** — any authenticated Member may publish one, by direct user request, deliberately overriding REQUIREMENTS.md's DB-3 "Won't (v1)" call (see Build Log below) and looser than `requireAnyTeamAdmin()` (Customer/Initiative creation). **`teamId`-set sharing was never granted that override** — it uses the exact rule `SavedView.visibility: "team"` already does (Team Member+ required; a Viewer may only save `"self"`), since a Team-scoped `DashboardView` is, for RBAC purposes, the same kind of resource a `SavedView` already is. Editing/deleting someone else's View always requires its creator, or (Team-level) Team Admin on that Team, or (Org-level) `requireAnyTeamAdmin()` — that floor exists on cleanup only, never on create, in both cases. |
| `config` | `Mixed` (`DashboardViewConfig`) | `{ widgets: WidgetInstance[] }` — array order is display order; no separate order field, same "stored/read/written wholesale" precedent `SavedView.config` set. |
| `createdAt` / `updatedAt` | `Date` | |

**Widgets are configurable instances, not a fixed kind selection** — the same kind can appear more than once with different filters/group-by, Asana-style, by direct user request (this replaced the feature's first-day version, which only let a Member toggle a fixed `WidgetKind[]`; `src/lib/dashboard-views.ts`'s `decodeDashboardViewConfig` still tolerates that older plain-string-array shape on decode, translating each legacy kind into an equivalent instance, so nothing already saved silently breaks). 5 kinds in the registry (`src/lib/dashboard-widgets.ts`):
- `summary` — the 4 stat tiles (open/closed/overdue/total), filterable.
- `breakdown` — one generic grouped-count widget **replacing** the first version's 3 fixed-shape cards (Priority/Team/Assignee breakdown); pick a `groupBy` (`priority`/`statusCategory`/`assignee`/`customerId`/`initiativeId`/`teamId`/`labels`) and a filter, and it renders a grouped open/closed/total table (`src/components/dashboard/breakdown-table.tsx`, capped at 12 visible groups with a real "+N more" note — `labels` in particular can produce far more groups than a fixed dimension ever could). `teamId` grouping/filtering is only offered on the Org Dashboard — a Team Dashboard's own scope is already one Team, so it would be a no-op dimension there.
- `cycle_time` — unchanged from the first version, still governed by the page's own Team/Initiative filter only, **not independently filterable per instance** this pass — a stated, deliberate scope line (it replays `ChangeHistory` per item rather than reading the page's one shared item fetch, so per-widget filtering would need its own querying path; recorded here rather than silently under-built).
- `burndown`/`velocity` — unchanged Sprint-scoped shape (`computeBurndown()`/`computeVelocity()`/`getActiveSprint()`, `src/lib/sprint-reports.ts`/`src/lib/sprints.ts`), but now with an **explicit per-instance Team pick** on the Org Dashboard (`WidgetInstance.teamId`) — decoupled from the page's own Team/Initiative filter bar, since a Sprint-scoped widget needs exactly one Team regardless of how many Teams the page itself has in scope. On a Team Dashboard the Team is already fixed by the URL, so no picker is shown (`WidgetGridScope.fixedTeamId`).

`WidgetGrid` (`src/components/dashboard/widget-grid.tsx`) is now an **async** Server Component — one `switch (instance.kind)` per widget instance, computing `summary`/`breakdown` from one shared, already-fetched item array (`fetchScopedWorkItems()`, `src/lib/dashboard.ts` — every widget on a page reuses this single Mongo query rather than issuing its own) filtered/grouped in memory (`src/lib/dashboard-filters.ts`'s `filterScopedItems()`, `src/lib/dashboard-breakdown.ts`'s `computeBreakdown()`), and fetching `burndown`/`velocity` per-instance only for those two kinds. Still the "generic engine, no bespoke path" point for this feature (Non-Negotiable #6): a 6th widget kind is one registry entry + one `case`.

**Per-widget filters are a deliberately separate, smaller engine from `src/lib/work-item-views.ts`'s `FilterConfig`** (`src/lib/dashboard-filters.ts`), not a forced reuse — see that file's own header comment for the full reasoning: a Dashboard widget can span every Team in the Org at once, where raw per-Team status keys don't mean anything comparable, so "status" here is the ORG-7-normalized `statusCategory` (4 fixed values), not a Team's own status vocabulary. Same two-level AND-of-OR shape, applied in plain JS over the already-fetched item array rather than a Mongo query.

**The widget picker always shows and allows adding every kind**, including `burndown`/`velocity` when the current Team filter is `"all"` or a Sprints-disabled Team — a deliberate reversal of the "invisible, not disabled" precedent `Team.sprintsEnabled` sets everywhere else (Sprint nav, the Sprint field). Reasoning, recorded here rather than left as an unexplained inconsistency: a `DashboardView`'s widget selection is a **stored, shareable config** that can be viewed later under a different Team filter, or applied by someone else as a `"shared"` view against a Team that doesn't have Sprints on — hiding the option based on today's transient filter would make the picker flicker every time the unrelated Team dropdown changes, and would make it impossible to pre-configure a View that only becomes valid later. Non-Negotiable #7 ("no screen may show nothing") is instead satisfied at **render time**, inside `WidgetGrid`'s own per-widget empty states (`"Pick a Team for this widget…"`, `"…hasn't turned on Sprints…"`, `"No active Sprint…"`) — not at picker time. Both Dashboard pages' data loaders only fetch `getActiveSprint()`/`computeBurndown()`/`computeVelocity()` when the active widget selection actually asks for them **and** a Team resolves (page-fixed on a Team Dashboard, per-instance-picked on the Org Dashboard) — the same "no unconditional extra query" discipline Phase 11 established for `dashboard/page.tsx`.

**Team Dashboards** (`/teams/[teamId]/dashboard`, `src/app/(app)/teams/[teamId]/dashboard/page.tsx`) — a genuinely separate surface from the Org Dashboard, not just that page's Team filter narrowed to one Team, by direct user request: its own Widgets menu, its own saved Views (`DashboardView.teamId` set, `"shared"` reaching that Team, not the whole Org), reached via a reciprocal "Dashboard" button on the Team's Work Items list and Board pages (same reciprocal-nav convention Phase 5 established for Board↔Task-list). `requireTeamRole(teamId, "viewer")` gates it — identical floor to every other Team-scoped read surface. `defaultTeamWidgetInstances()` swaps the Org default's "By Team" breakdown for "By Status" (grouping by Team is a no-op when the whole page is already one Team).

### Phase 11 — Navigation & Data-Fetch Performance (August 15, 2026)

**Root cause, confirmed by direct reading of this repo's bundled Next.js 16 docs (`node_modules/next/dist/docs`, per AGENTS.md — this Next version has breaking changes from training-data assumptions), not assumed from prior Next.js experience:** every authenticated page rendered `<AppShell>` **inline inside its own `page.tsx`/`loading.tsx`** rather than from a shared `layout.tsx` — a Phase 2 decision whose own comment stated a shared layout "wouldn't" re-render on navigation, keeping the notification bell fresh only by re-querying on every page render. That belief was backwards for this Next.js version: per `01-app/01-getting-started/03-layouts-and-pages.md` and `04-linking-and-navigating.md`, a real `layout.tsx` "preserve[s] state, remain[s] interactive, and do[es] not rerender" on client-side `<Link>` navigation between the pages beneath it — this is ordinary App Router partial-rendering behavior, unrelated to Cache Components (confirmed `cacheComponents` is **not** set in `next.config.ts`, so this phase used the "previous model" caching primitives — `React.cache`, route restructuring — documented in `02-guides/caching-without-cache-components.md`, not `"use cache"`/`cacheLife`). The result: `AppShell`'s `auth()` call plus `listNotificationsForMember()` (4 Mongo operations — `Notification.find`, `Notification.countDocuments`, `Team.find`, `Member.find`, `src/lib/notifications.ts`) were re-running on **every single navigation** in the app, not just on a real change.

**1. Shared authenticated layout** — every authenticated route (`dashboard`, `my-teams`, `boards`, `customers`, `guest-access`, `initiatives`, `settings/*`, `teams/[teamId]/*`, `work-items`) moved into a new route group `src/app/(app)/` (route groups add no URL segment — every existing URL is unchanged, confirmed by the build's route table). `src/app/(app)/layout.tsx` is now the single place that calls `getCurrentMember()` (the unauthenticated `redirect("/login")` gate, previously duplicated per-page — each page still calls it too for TypeScript null-narrowing and defense in depth, but it's a cache() hit, not a second query) and `listNotificationsForMember()`, then renders `<AppShell>`. `AppShell` itself (`src/components/layout/app-shell.tsx`) is now a plain presentational component taking `session`/`notifications`/`unreadCount` as props instead of fetching them itself. All 21 `page.tsx` and 18 `loading.tsx` files had their inline `<AppShell>` wrapper stripped (mechanical, verified by `grep -rl AppShell src/app/(app)` returning only `layout.tsx` afterward) — as a side effect, a slow navigation's `loading.tsx` skeleton no longer re-flashes the whole nav chrome, only the page content area. `router.refresh()` (used by ~18 mutation call sites) still re-runs this layout, which is correct — a mutation can change notification state; only passive navigation between pages is now cheap.

### Dashboard Views — Per-Widget Filters & Team Dashboards (same-day expansion) (August 17, 2026)

**Direct follow-up user request, same session as the entry above**: "need widgets like asana as well — so that people can configure the filters and other attributes too — not just on org level but team level dashboards too." A Dashboard widget can span every Team in the Org at once, where "status" only means anything via the ORG-7-normalized `statusCategory` (the same "compare across Teams" problem `computeDashboard()` already solved by bucketing on category, not raw status) — so this file re-establishes the same two-level AND-of-OR shape as a parallel, smaller model over a Dashboard-specific field set (`priority`/`statusCategory`/`assignee`/`customerId`/`initiativeId`/`labels`/`teamId`). On a Team Dashboard, `fixedTeamId` is always set (the page's own Team), so no picker is ever shown there — the field is simply irrelevant on that surface, not hidden-but-still-asked.

**`/teams/[teamId]/dashboard`** (`src/app/(app)/teams/[teamId]/dashboard/page.tsx`) — `requireTeamRole(teamId, "viewer")`, same read floor every other Team-scoped page uses. ### Time Tracking (WL-1–WL-5) — deliberate REQUIREMENTS.md override (August 18, 2026)

**This reverses a documented `Won't (v1)` call, by direct user instruction.** REQUIREMENTS.md §12 ("Explicitly Out of Scope for v1") explicitly listed "Time tracking / worklogs." The user asked directly for Team members to log actual time spent on a Work Item **per calendar day** (not Asana's "only visible once the task is completed" behavior), in a unit each Team configures (Story Points or Hours/Minutes), plus an independent Estimate on the Work Item with no automatic reconciliation between the two. REQUIREMENTS.md's §12 line is struck through in place with an override note, and a new §7.12 records WL-1 through WL-5 — same treatment the Sprint/Initiative unification and Dashboard Views overrides were given, not silently built past.

Several design decisions were confirmed with the user directly before/during implementation, stated here as the reasoning behind choices a future reader might otherwise second-guess:
1. **Unit is a per-Team setting**, not per-item or org-wide — a Team Admin picks Story Points *or* Hours/Minutes for their whole Team, same shape `Team.sprintsEnabled` already established for an opt-in-per-Team feature.
2. **Multiple log entries per person/item/day are allowed** — logging time twice on the same item on the same day creates two rows, not one edited row.
3. **Any Team Member+ can log time** against any Work Item they can already see — not restricted to the assignee.
4. **The Actual rollup is a real-time, automatic, database-persisted value — not a live aggregate-on-read, and not a scheduled/cron recompute.** The user's own framing: "computing per day and saving is fine — but I should have an option to recompute it after X days either automatically/manually," then, once asked to disambiguate, simplified to "let the values be rolled-up in realtime and updated in the db alongwith the already saving function daily" / "automatic only." This landed as `WorkItem.actualTotal`, recomputed and written back synchronously by every `WorkLog` mutation (`recomputeWorkItemActualTotal()`) — deliberately **not** a second automation-engine override (REQUIREMENTS.md §12 still excludes an automation/rules engine): nothing runs on a schedule or without a person's own save action triggering it.

**Why a new `WorkLog` model instead of a new `ChangeHistory.kind`** (the design fork resolved before writing any code): `ChangeHistory` is a hard, append-only invariant (Non-Negotiable #5 — "no route anywhere may update or delete a document here, for any role"). A daily log a person needs to correct ("logged 3h, meant 2.5h") cannot live there without breaking that guarantee for every other kind sharing the collection. `WorkLog` is an ordinary mutable model — the one collection outside `ChangeHistory` a Member can edit/delete their own past write to — while a `"work_log"` `ChangeHistory.kind` still records an add/edit/remove breadcrumb for traceability, same division of responsibility `"attachment"` rows already have (see the `WorkLog`/`ChangeHistory` model entries in §4 above for the full field-level design).

**Estimate vs. Actual stay genuinely independent** (WL-2) — `WorkItem.estimate` is a plain Team-Member-editable number, never computed from or reconciled against `actualTotal`; the `estimate_vs_actual` Dashboard widget (WL-5) shows both side by side plus a variance column, but never writes one from the other.

**Coordination note**: this work landed in the same working tree as an unrelated, concurrent "Load More" pagination redesign (list-view aggregation pipeline, `src/lib/work-item-page-query.ts`/`work-item-row.ts`) touching `WorkItem.ts`'s indexes and `work-items-table.tsx`. The two efforts were kept to non-overlapping files by construction — this phase's `WorkItem.ts` changes are two new fields (`estimate`, `actualTotal`), never an index or the pagination query path — and `history-feed.tsx`'s `HistoryEntry.kind` union (widened to include `"work_log"` by the concurrent session once it hit this phase's in-flight `ChangeHistory.kind` change) was left as the concurrent session's own minimal, safe fallback rendering rather than re-touched here, to avoid two sessions editing the same file at once.

### Pagination / "Load More" + query-performance rewrite (August 18, 2026)

Direct code read confirmed the root cause the user reported ("pages feel slow, will get worse as data grows"): almost every list-rendering query fetched its **entire** matching result set with no `.limit()` — `WorkItem.find(...).sort(...).lean()` (Work Items list + Board), `Customer.find(...).sort({name:1})`, `Initiative.find(...).sort({name:1})`. Only Search, Notifications, and the Audit Log already capped results. Two follow-up design decisions were confirmed with the user before writing code (both the thorough option over the minimal one, per the approved plan `lazy-baking-breeze.md`), each its own checkpoint with explicit before/after verification:

1. **Work Items' Group-By and custom sort** (status/priority/assignee-name — previously computed in-JS on the full fetched array, since semantic order isn't alphabetical) rewritten as a real MongoDB **aggregation pipeline**, not left unpaginated as a stated gap.
2. **Kanban Board's drag-and-drop reorder** — previously a client-computed fractional `order` via `orderBetween()`, which only works if the client already holds every sibling in a column — redesigned to compute `order` **server-side**, re-deriving the true DB-adjacent sibling rather than trusting the client's belief about what's at the edge of a (now paginated) column/list.

**Design 1 — aggregation rewrite.** `src/lib/work-item-page-query.ts` (new file — deliberately **not** merged into `src/lib/work-item-views.ts`, which is intentionally DB/mongoose-free because a client component, `view-toolbar.tsx`, imports its pure types; adding a mongoose import there would risk pulling server-only code into the client bundle graph) exports `getWorkItemsPage()`, replacing the old in-JS `applySort`/`applyGroupBy` (removed once the rewrite was confirmed equivalent — see Verification). Status/priority rank via `$indexOfArray` against the Team's live `Workflow.statuses[]` order / the fixed `PRIORITIES` scale (unmatched → rank `0`, matching the old `?? 0` fallback exactly, not `-1`); assignee-name sort via a literal `$indexOfArray` lookup against the Team's mention-candidate list (`getTeamMentionCandidates`) rather than a raw `$lookup` against the full `Member` collection — the old comparator only ever resolved names through that Team-scoped set (same set the assignee field-option picker offers), defaulting to `""`/"Unknown" for anyone outside it, and a raw `$lookup` would have resolved *any* valid Member id regardless of Team membership, a real behavior mismatch caught during verification, not a theoretical one. The Work Item `key` (e.g. `"DEV-42"`) sorts by its numeric suffix (`$split`+`$toInt`), reproducing the old `localeCompare(..., {numeric:true})` instead of lexicographic order. `dueDate` sort substitutes `Number.MAX_SAFE_INTEGER` for a missing date (Mongo's native null-sorts-first in ascending order is the opposite of the old comparator's `?? Infinity`). Group-by needs no `$unwind` — confirmed by direct read that `GROUPABLE_FIELDS` (work-item-views.ts) does not include `"labels"`, the one array-valued filterable field; every groupable field is single-valued. Group *order* (which section renders first) is not alphabetical or rank-order — the old code always ran `applySort` across the whole item set first, then bucketed the already-sorted array, so a group's position is "wherever its first item landed in the overall sort" (default sort is `updatedAt` desc, so group order comes out effectively recency-randomized) — reproduced by capturing each group's first-encountered document (`$first` on the already-sorted stream) and re-sorting the group summaries by that document's own computed sort fields. A deliberate, genuine addition beyond old-behavior parity: every sort spec appends `_id: 1` as a final tiebreak (after falling back to `updatedAt: -1` as the implicit secondary key when the user's chosen sort doesn't already include it, matching the old code's actual stable-sort-over-an-updatedAt-desc-fetched-array behavior — confirmed as a real, visible mismatch when this was first built as `_id`-only, not merely a theoretical edge case) — old code had no tiebreak at all for equal-timestamp ties, which would make pagination page-to-page non-deterministic (silently duplicating or dropping a row) without one. Response shape: `{items,total,page,pageSize,hasMore}` flat mode, `{groups:[{key,label,items,total,page,pageSize,hasMore}]}` grouped — grouped mode paginates **per group** (each group's own first page, capped at 50, own `hasMore`), not one global page across every group, via a dedicated cheaper `$match`-only path (no `$group` stage) for a specific group's subsequent "Load More" page. `GET /api/teams/[teamId]/work-items` now serves three shapes from one route, chosen by which query params are present: no `view`/`page`/`pageSize`/`groupKey`/`mode` → the **original**, byte-for-byte `{workItems}` full-array/`type`-only-filter shape (several existing pickers — sub-task parent, cross-team link, origin — already call this exact shape needing the *full* matching set to search client-side, confirmed by grep before touching the route); `view`/`page`/etc. present → the new paginated `getWorkItemsPage()` shape, rows pre-resolved server-side (`src/lib/work-item-row.ts`'s `toWorkItemRow`/`buildRowMaps`, shared between the list page's first-page render and this route's subsequent pages so a page-2 row looks identical to page-1); `mode=board` → a third, simpler shape (below).

**Design 2 — server-side authoritative reorder.** `PATCH .../work-items/[itemId]` gains `reorder: {scope:"column"|"team", afterItemId, beforeItemId}` (`src/lib/work-item-reorder.ts`'s `resolveServerOrder()`), alongside the existing raw `order` field (kept working, mutually exclusive — 400 if both given — for non-drag callers like bulk-edit). `scope:"column"` matches `{teamId,type,status}` (Kanban — same-column reorder or a cross-column drop, always scoped to the item's post-move status); `scope:"team"` matches `{teamId,type}` with no status filter (Backlog — one flat, all-statuses priority queue). The server looks up each claimed neighbor's *current* `order` by id (never a client-sent order number), then — the actual fix — re-derives the true DB-adjacent sibling on whichever side is "open" (a `null` id, or a stale id that no longer resolves in scope) by querying for the real next/previous sibling, instead of assuming a `null` side means the genuine end/start of the column. A same-column interior drop and a boundary drop at the edge of a partially-loaded page are the same code path here — the server never trusts "this is the end" from the client, it always re-checks. A real bug was found and fixed during this checkpoint's own verification: the first draft built the neighbor-lookup filter as `{_id: afterItemId, ...scopeMatch}` where `scopeMatch` also carried `_id: {$ne: itemId}` — object-spread key collision silently discarded the intended `_id` equality match, making every lookup match "any item in scope" instead of the specific neighbor. Caught by a dedicated correctness test script before this ever reached a real drag. Client changes (`kanban-board.tsx`/`backlog-list.tsx`/`board-view.tsx`): `handleDragEnd` still computes a placeholder `order` via the existing `orderBetween()` for *immediate optimistic visual feedback only* (smooth drag, no snap-back before the request round-trips), but sends `reorder` (predecessor/successor **ids**, not the client-computed order) as the actual PATCH payload; `board-view.tsx`'s `persist()` now reconciles local state to the server's returned authoritative `workItem.order` once the request resolves — the old code never did this (the client-computed value was silently trusted as final), which stopped being safe once the server's real value can legitimately differ from the client's guess at a pagination boundary.

**Design 3 — "Load More," per surface.** One shared `src/components/shared/load-more-button.tsx` (real loading spinner state, real "All N loaded" end state, real error toast on fetch failure — Non-Negotiable #7) reused by all four surfaces rather than four bespoke implementations.
- **Work Items list**: `src/components/work-items/load-more-work-items-table.tsx` wraps the existing `WorkItemsTable`, seeded from the server-rendered first page. Flat mode is modeled as a single implicit group (`key:"__all__"`) so grouped and flat modes share one code path inside `WorkItemsTable` (which now renders a per-group `LoadMoreButton` when a group carries `onLoadMore`) — deliberately **one** `WorkItemsTable` instance for every group rather than one instance per group section, since `WorkItemsTable` owns the multi-select bulk-edit state internally and splitting into separate instances would silently break today's cross-group bulk selection (selecting items from two different status groups and bulk-applying to both at once).
